# wmux MCP vNext — Model-Native, Measurable, and Dual-Era

**Status:** Accepted direction; Phase 0 complete, Phase 1 proceeding through
wire-neutral catalog slices on `feat/mcp-vnext-foundations`

**Date:** 2026-07-28

**Scope:** wmux's local MCP server, broker boundary, tool catalog, permissions,
and long-running operations

## Executive decision

Evolve the existing `wmux` MCP server. Do not replace it with a collection of
domain servers, a generic `wmux_call` dispatcher, or a wmux-specific
`search_tools` meta-tool.

The target is one stable server identity with a deterministic typed catalog,
immutable launch-time profiles, transport-authenticated callers, durable jobs,
and protocol adapters for both the stable 2025 MCP era and the eventual 2026
era. The operation core must not depend on either MCP wire format.

This is a better fit for current frontier models than making the tool surface
artificially tiny:

- Claude Code defers MCP schemas by default and initially loads only tool names
  plus server instructions. It already owns tool discovery.
- OpenAI tool search can defer an entire MCP server and Programmatic Tool
  Calling can invoke loaded MCP tools. It also owns tool discovery and
  orchestration.
- Fable 5, Opus 5, and GPT-5.6 Sol are all better at long, tool-heavy work.
  Their common requirement is a truthful, deterministic, typed tool contract,
  not another model-facing dispatch language.

The design should therefore optimize for semantic precision, side-effect
safety, resumability, and observable progress. Raw schema size remains a wire,
startup, compatibility, and memory concern, but it is no longer a reason to
discard typed tools.

## Evidence as of 2026-07-28

### Model and host changes

| Change | Design consequence for wmux |
| --- | --- |
| Claude Fable 5 targets days-long, asynchronous work and long-running agents. | Long work needs durable job state, progress, cancellation, and recovery outside a single model turn. |
| Claude Opus 5 emphasizes careful iteration, root-cause work, and higher consistency with fewer turns. | Give the model exact effects and structured results; do not induce redundant verification with ambiguous outcomes. |
| GPT-5.6 Sol adds Programmatic Tool Calling, multi-agent beta, persisted reasoning, and explicit prompt caching. | Make safe read operations composable and machine-readable; preserve a stable catalog and cache-friendly instructions. |
| Claude Code tool search is on by default and loads only names and server instructions initially. | Add concise server instructions; do not build a competing `search_tools` tool. |
| OpenAI tool search defers MCP tools and loads them before a program can call them. | Keep typed MCP tools independently callable and mark effects accurately. A generic dispatcher would erase this value. |

Model launch claims are inputs, not acceptance evidence. Any model-specific
optimization must be evaluated on representative wmux tasks across at least
Claude Code, Codex, and one additional MCP host.

### Live wmux baseline

The bundled server was probed through the public MCP Client over real stdio:

| Profile | Tools | `tools/list` JSON | Schema metadata |
| --- | ---: | ---: | --- |
| `full` | 84 | 69,726 bytes | No titles, annotations, or output schemas |
| `commander` | 37 | 41,121 bytes | No titles, annotations, or output schemas |

Additional findings:

- The 39 `browser_*` tools dominate the full surface.
- Before Phase 0, common source, dist, and stable-copy layouts could advertise
  `serverInfo.version = "0.0.0"` even when the package version was known.
- Eleven persistent stdio MCP children consumed roughly 433 MB of private
  memory in one live sample. The broker can address this, but is not ready to
  become the default.
- The catalog is registered through many modules. Commander mode monkey-patches
  the deprecated SDK registration method to filter it.
- Client-provided `clientInfo.name` currently participates in legacy permission
  behavior. It is self-declared telemetry, not authentication.
- `.mcps/` or `mcps/` content is generated integration cache. It is not a
  source directory and must not be edited, committed, or packaged.

### Protocol release race

The stable MCP specification is still `2025-11-25`. The official specification
repository marks `2026-07-28` as an RC and explicitly says it is not final.
Meanwhile, `@modelcontextprotocol/server@2.0.0` was released on 2026-07-27.
Those are separate facts: an SDK major release does not make an untagged
protocol revision safe to adopt in production.

The 2026 revision is a real architectural change, not a routine upgrade. It
introduces a stateless/sessionless core, `server/discover`, per-request metadata,
extensions, Tasks, subscriptions, caching hints, MCP Apps, authorization
hardening, and full JSON Schema 2020-12 behavior. It also removes or restructures
parts of the legacy lifecycle.

wmux must remain 2025-compatible. A future 2026 implementation is a negotiated
adapter, never a modern-only cutover.

## Product contract

### One server key, static profiles

Keep the user-facing server key `wmux`.

Profiles are selected once at process launch and never mutate during a session:

- `full` remains the compatibility default.
- `commander` remains a security role with a deliberately smaller surface.
- `core` may be added later as an explicit optimization profile for terminal,
  pane, workspace, channel, and delegation work without browser/company tools.

Do not choose a profile from a model name. Do not emit `tools/list_changed` to
swap domains in and out while a task runs. A host's cache, approval records, and
model context should see one immutable contract for the process lifetime.

The optional `core` profile should use the same server key and implementation,
selected by an explicit launch argument. Splitting terminal, browser, channel,
and delegation into separate MCP children would multiply configuration,
authentication, lifecycle, memory, and cross-domain planning costs.

### Native discovery, not a meta-tool

Do not add `search_tools`.

Do not collapse tools into:

```text
wmux_call({ operation, arguments })
```

Both approaches hide input schemas, output schemas, approval boundaries,
effect annotations, and per-tool audit records from the host. They also make
Programmatic Tool Calling less safe because every operation appears to have the
same generic effect.

Tool names should continue to use clear domain prefixes. Server instructions
should describe when to search wmux, list the major domains, and put critical
routing and trust rules in the first 512 characters. Each instruction string
must remain below 2 KiB.

## Target architecture

```text
MCP host
  |
  v
stable bootstrap shim
  |-- broker healthy --> shared broker transport
  `-- unavailable ----> full child fallback (before initialization only)
                             |
                             v
protocol adapter (2025; later negotiated 2026)
                             |
                             v
immutable catalog profile --> authenticated principal + policy
                             |                 |
                             v                 v
                       operation core ----> approval ledger
                             |
                  +----------+----------+
                  |                     |
             immediate result       durable JobEngine
                                           |
                                get / wait / events / cancel
```

The boundaries matter:

1. **Protocol adapter** translates an MCP era into internal requests.
2. **Catalog registry** owns schemas and profiles, then proven execution
   metadata and result codecs as later phases add them.
3. **Principal and policy** decide authorization independently of model-facing
   metadata.
4. **Operation core** implements wmux behavior without MCP SDK types.
5. **JobEngine** owns durable lifecycle for work that can outlive a call.

This separation lets wmux adopt a new SDK or protocol without rewriting
permissions and operations at the same time.

## Typed catalog

Replace distributed registration plus commander monkey-patching with one
descriptor type, one domain at a time. The Phase 1 migration contract is
deliberately smaller than the target execution contract:

```ts
type ToolProfile = 'full' | 'core' | 'commander';

interface OperationContext {
  principal: { kind: 'unattributed' };
}

interface WmuxToolSpec<Name extends string = string> {
  name: Name;
  description: string;
  inputSchema: z.ZodRawShape;
  profiles: readonly ToolProfile[];
  invoke(
    input: Record<string, unknown>,
    context: OperationContext,
  ): CallToolResult | Promise<CallToolResult>;
}

declare function defineWmuxTool<
  const Name extends string,
  const Shape extends z.ZodRawShape,
>(draft: {
  name: Name;
  description: string;
  inputSchema: Shape;
  profiles: readonly ToolProfile[];
  invoke(
    input: z.infer<z.ZodObject<Shape>>,
    context: OperationContext,
  ): CallToolResult | Promise<CallToolResult>;
}): WmuxToolSpec<Name>;
```

The current adapter passes only `description` and the existing raw Zod shape to
`McpServer.registerTool`. It does not publish `title`, annotations, or an output
schema, and it does not rebuild schemas through an intermediate JSON Schema
representation. This keeps validation, property ordering, approval UI, and the
raw `tools/list` bytes unchanged while registration moves off the deprecated
`server.tool()` API.

Exact input inference exists at the `defineWmuxTool` authoring boundary; the
heterogeneous runtime registry deliberately erases it to
`Record<string, unknown>` once, after which the SDK validates through the raw
Zod shape before invocation. The helper and registry boundary both shallowly
freeze descriptor, profile, and raw-shape containers.

`OperationContext` always exists but does not contain the selected profile.
Today its only principal is explicitly `unattributed`; profile, annotations,
and self-declared `clientInfo` never create authority. A future authenticated
transport principal requires a private branded constructor rather than another
public structural variant.

Do not add static effects, retry, timeout, or lock declarations merely to fill
out the target shape. Several browser tools select read/write/destructive
behavior from their arguments; apparent reads can auto-open a browser or
acquire an automation lease; pane close affects its surfaces and parent
layout. The eventual execution contract therefore needs:

- argument-sensitive effect and retry classifiers, with public annotations
  derived from the worst case across valid inputs;
- canonical targets resolved after authentication;
- a multi-resource lock resolver with deterministic lock ordering;
- cancellation and deadline semantics that distinguish known-no-effect from
  an ambiguous dispatched mutation;
- an observed downstream RPC closure for drift tests.

The downstream declaration is not an allowlist. `RpcRouter`,
`PermissionEnforcer`, and `METHOD_CAPABILITY` remain the daemon's only
execution authority. If a future descriptor has no RPC transport, represent
that explicitly; an empty methods array must never mean both "local" and
"forgotten".

After every domain is migrated and the classifiers above are proven, generate
standard MCP annotations, permission-drift tests, structured result codecs,
protocol documentation, and the `full`, `core`, and `commander` surfaces from
the catalog. Only then canonicalize the complete public descriptor set into a
`catalogRevision`; a partial catalog revision would be misleading. The same
build and profile must always produce the same revision and ordered
`tools/list` response. Send a list-changed signal only when that revision
genuinely changes.

## Results and long-running work

Add `outputSchema` and `structuredContent` incrementally, starting with
high-value read tools such as workspace, pane, terminal-event, channel, and
task queries. Keep the equivalent serialized JSON in a text content block for
older hosts, as the stable MCP specification recommends.

Do not turn every slow operation into a long synchronous tool call. The
operation core should expose:

```text
submit -> jobId
get(jobId) -> current state
wait(jobId, cursor, timeout) -> bounded update
events(jobId, cursor, limit) -> ordered durable events
cancel(jobId, reason) -> terminal or cancellation-pending state
```

Required properties:

- durable across MCP reconnects and host restarts where the underlying wmux
  operation survives;
- monotonic state transitions and cursors;
- bounded waits with heartbeats or progress;
- cancellation that is explicit about whether the underlying effect stopped;
- idempotency keys for eligible mutations;
- approval records bound to principal, tool, canonical argument hash, call/job
  id, expiry, and catalog revision;
- ambiguous timeout responses that tell the caller how to inspect state before
  retrying.

The future MCP Tasks extension should adapt to this JobEngine. It must not
become wmux's only job representation because legacy hosts still need the same
recovery semantics.

## Identity, authorization, and untrusted data

`clientInfo` is telemetry. A caller can choose it, and the 2026 protocol makes
it per-request and optional at the protocol level. It must not become a
security principal.

The eventual principal must be issued and validated by wmux's transport or
bootstrap boundary and include the role and relevant process/session binding.
The policy layer consumes that principal; it never infers privilege from a
model or host name.

Migration from current legacy behavior should be explicit:

```json
{
  "mcp": {
    "legacyClients": "allow"
  }
}
```

Support an observed deprecation period, then allow users to switch to `deny`
before changing the default. Log legacy use without silently widening it.

All terminal, browser, repository, channel, task, and metadata content is
untrusted input to the model. Tool descriptions and server instructions must
say so. MCP annotations are also untrusted hints from a host's perspective and
must never authorize a call.

For stdio, stdout is exclusively the JSON-RPC transport from process start
through shutdown. Every diagnostic belongs on stderr.

## Broker completion gates

The shared broker remains an optimization behind the same protocol contract.
It is not ready for default-on until all of these are true:

- the shim falls back to a full child if the broker is unavailable, but only
  before MCP initialization;
- a mid-session broker loss makes the shim exit non-zero; it never silently
  rebinds a live session;
- admission control limits concurrent connections and memory growth;
- auth tokens can rotate without restarting every configured host;
- claimed PID/parent/environment hints are validated at runtime where the
  platform permits;
- the main pipe becomes ready independently, so broker readiness cannot delay
  core wmux startup;
- shutdown and stale-socket behavior is covered on Windows and macOS;
- a 10-host benchmark shows at least 50% lower aggregate private memory than
  the current child-per-host topology without a material initialization
  regression.

Operational diagnosis belongs in a repo-relative transcript probe and,
eventually, `wmux mcp doctor`. A `wmux_status` MCP tool cannot diagnose a
transport that failed before tools were available.

## 2026 protocol and SDK adoption gates

Do not migrate production code to the TypeScript SDK v2 merely because 2.0.0
exists. Begin the migration only when:

1. the final `2026-07-28` specification tag exists;
2. the TypeScript SDK has at least one post-GA patch release or the relevant
   blockers are independently verified fixed;
3. the typed catalog has replaced the current registration monkey-patch;
4. golden transcripts show no accidental 2025 surface or schema changes;
5. Claude Code, Codex, Gemini CLI, and the wmux commander profile pass the host
   matrix;
6. the server passes official conformance tests for every advertised era;
7. downgrade and mixed-version behavior is tested.

Adopt in two steps:

1. Port to SDK v2 while still advertising and testing only the stable legacy
   protocol.
2. Add explicit 2026 negotiation and keep the legacy adapter enabled.

Do not enable tool pagination until all supported hosts consume every page.
Past host behavior has included first-page-only implementations. Resources may
paginate independently when tested.

## Rollout

### Phase 0 — truthful and measurable (implemented here)

- Inject the package version into self-contained MCP and broker bundles.
- Resolve source/dist/stable layouts without assuming one relative path.
- Refuse startup if every version source is missing or invalid; never advertise
  a synthetic `0.0.0`.
- Add concise profile-aware server instructions.
- Keep shutdown diagnostics off stdout.
- Replace the hard-coded commander smoke script with a repo-relative public
  Client probe.
- Freeze exact full/commander names, raw result hashes, and instruction hashes,
  enforce payload budgets and stdout framing, and run the probe in CI.

### Phase 1 — catalog without behavior change

- Introduce `WmuxToolSpec` and migrate one domain at a time.
- Begin with pane/surface lifecycle: five tools on `registerTool`, literal-name
  and Zod inference, immutable full/commander profiles, and explicit
  unattributed `OperationContext`.
- Follow with the single full-only `browser_wait` tool to prove that catalog
  selection removes a tool from commander without changing its automation
  lease, Playwright/RPC fallback behavior, schema order, or global wire order.
- Migrate the twelve channel/mission tools only after a test-only baseline pins
  every RPC mapping, raw-shape order and identity, optional-field behavior,
  per-invocation sender lookup, and multi-server resolver isolation. Build the
  catalog per server connection; never hoist specs that capture channel deps.
  All twelve remain in both full and commander, including
  `channel_mission_close`.
- Derive one immutable registration profile and unattributed context per server
  instance, and reuse shared commander-lockstep/freeze assertions across
  migrated domains.
- Keep title, annotations, output schemas, effect claims, and policy authority
  off the wire during the migration.
- Require commander catalog entries to equal the intersection of the legacy
  commander manifest and migrated-domain names while both sources coexist.
- Exercise exact wire parity on `2025-11-25`, `2025-03-26`, and `2024-11-05`.
- Add argument-sensitive effect, retry, lock, and downstream-closure metadata
  only with behavioral truth tests; use it to audit, never to authorize.
- Remove the `server.tool` monkey-patch only after surface parity is proven.
- Add an opt-in static `core` profile after host evaluation.

### Phase 2 — typed reads and diagnostics

- Add output schemas plus text fallbacks to high-value read operations.
- Add `wmux mcp doctor` for bundle, version, config target, handshake, pipe,
  broker, and permission diagnostics.
- Add cross-host scenario tests and tool-selection quality metrics.

### Phase 3 — durable operations

- Implement JobEngine, bounded waits, cursored events, cancellation, and
  idempotency keys.
- Bind approvals to canonical operations and durable jobs.

### Phase 4 — broker hardening

- Complete the broker gates, benchmark it, then move from opt-in to `auto`.
- Preserve pre-initialize child fallback and fail loudly after session loss.

### Phase 5 — SDK v2 and dual-era protocol

- Port registration through the typed catalog.
- First preserve 2025 behavior; then negotiate 2026 behind a feature gate.
- Add Tasks as a JobEngine adapter and verify mixed-era downgrade paths.

### Phase 6 — optional MCP surfaces

- Add resources for large, addressable read results where they reduce repeated
  payloads.
- Add prompts only for genuinely reusable user-invoked workflows.
- Add MCP Apps only where an interactive UI is better than the existing wmux
  surface.

## Acceptance criteria

### Compatibility and determinism

- The default profile has no renamed or removed tool without an intentional
  compatibility plan.
- Full and commander surfaces match reviewed golden baselines.
- Commander ordering equals the full registration order filtered by the
  commander membership set.
- Two consecutive raw `tools/list` result values are byte-identical (request
  IDs and their envelopes are excluded).
- Stable and representative legacy protocol clients negotiate their requested
  version while receiving the same reviewed tool descriptors.
- `serverInfo.version` equals `package.json` in real bundled, unbundled-dist,
  and relocated-bundle handshakes. Unit tests cover the source-tree and
  adjacent stable-marker resolution paths.
- Instructions are present, self-contained in their first 512 characters, and
  no larger than 2 KiB.
- Structured output always retains a legacy text fallback.

### Safety

- No self-declared client or model string grants authority.
- No annotation grants authority.
- Catalog declarations never grant an RPC method; daemon routing, capability,
  and permission enforcement remain authoritative.
- Catalog invocations carry an explicit operation context; an unattributed
  principal cannot be upgraded from profile or client metadata.
- Profile selection is immutable and cannot widen after initialization.
- Ambiguous mutations are never blindly retried unless their contract is
  explicitly idempotent.
- stdio stdout contains complete JSON-RPC protocol frames only, including
  during shutdown.

### Performance and reliability

- Full `tools/list` stays at or below 75,000 bytes until a reviewed baseline
  change; commander stays at or below 45,000 bytes.
- Catalog order and hash are deterministic across repeated builds.
- Broker default-on meets its memory, admission, startup, fallback, and
  cross-platform gates.
- Long work remains observable and recoverable after an MCP reconnect.

### Protocol evolution

- Every advertised version passes conformance and host-matrix tests.
- The 2025 adapter remains available during 2026 rollout.
- No production dependency on an RC protocol or undocumented private SDK API.
